# Plan: ADR — a preemptible kernel is a non-goal

Register the project-wide decision that a preemptible kernel is a
non-goal, so every design decision assumes a non-preemptible kernel
with no adaptation layer and no no-op preemption flag. The lock crate
already records this for locks only
(`crates/lock/docs/adr/0008-preemption-is-a-non-goal.md`); that record
becomes an application of the system decision, not a second source.

Writing rules applied (`writing-for-agents` + repo ADR style from
`crates/lock/docs/adr/`): leading words *non-preemptible* and
*non-goal*; positive target (design for the kernel as it is) paired
with the hard guardrail (no adaptation, no no-op flag); single source
of truth (system ADR owns the decision, lock ADR owns lock fallout);
no always-on duplication beyond one AGENTS.md rule.

Scope trap to write around: *non-preemptible* means **kernel-mode
preemption only**. Mach's `thread_setrun(…, may_preempt)` / AST
preemption of the current thread at kernel exit, and an interrupt
running on top of a callout action, stay in scope as they are. An
agent that reads "preemption is a non-goal" and deletes
`may_preempt` has misread the ADR. The body therefore defines the
term operationally ("leaves its CPU in kernel mode only by blocking")
and never uses bare *preemption* for the AST path.

## 1. `docs/adr/0001-preemptible-kernel-is-a-non-goal.md`

Follow the lock-crate ADR shape (title, short body, optional
`## Considered Options` / `## Consequences`). No status frontmatter —
accepted by default, as in lock ADR 0001/0005–0010. No SPDX header:
none of the ten lock ADRs carry one, and root markdown has no
precedent either (`CONTRIBUTING` licenses source files; these are
records, not source). Match that.

```md
# A preemptible kernel is a non-goal

The kernel is non-preemptible: a thread leaves its CPU in kernel mode
only by blocking. Every design decision takes that as given. The
non-preemptive shape is the design, not a special case of a preemptive
one: no adaptation layer and no no-op flag stand in for a future
preemptible kernel. A thread still leaves the CPU at a trap or an AST
check when a higher-priority thread is runnable; that is scheduling,
not kernel preemption.

## Considered Options

- **Design for a preemptible kernel with hooks that do nothing today**
  (the earlier choice, still visible for a while in the lock crate):
  every API carries a preemption section or flag that is a no-op until
  kernel preemption arrives. Rejected: those hooks and flags shape
  every design for a kernel that does not exist, and a no-op flag
  hides the real contract.

## Consequences

- Locks, RCU quiescent states, callouts and critical sections are sized
  for a CPU that keeps its kernel context until the thread blocks or an
  interrupt returns.
- Making the kernel preemptible later is a new decision, not a
  configuration change. It reopens the lock crate
  (`crates/lock` ADR 0008), the RCU quiescent-state definition, and
  every assumption that there is no preemption point between a load
  and its use.
```

Why this wording:

- *Non-preemptible* is defined operationally ("leaves its CPU in kernel
  mode only by blocking") so an agent can check a design against it.
  The closing sentence of the first paragraph draws the line at AST
  scheduling (`may_preempt`, trap-return reschedule) so the ban does
  not bleed into Mach's normal preemption-at-kernel-exit path.
- "Every design decision takes that as given" is the scope the user
  asked for — not locks-only, not opt-in.
- The guardrail is paired with the positive target ("the
  non-preemptive shape is the design") so attention lands on what to
  do, not only on the ban.
- `## Considered Options` records the rejected "hooks for later"
  path so the next agent does not reintroduce it as a kindness.
- `## Consequences` is the non-obvious fallout: what stays true
  (sizing of sections), and what a future preemptible kernel would
  actually cost.

## 3. `crates/lock/docs/adr/0008-preemption-is-a-non-goal.md` — defer

Keep the lock-specific body and consequences; stop restating the
system decision as if it were this crate's. First paragraph becomes
the application; consequences stay (they are lock-only).

```md
# Preemption is a non-goal

Applies [ADR 0001](../../../docs/adr/0001-preemptible-kernel-is-a-non-goal.md)
to this crate. Kernel code is never preempted, so the crate has no
no-preempt sections, no preemption hooks in `Platform` and no
preemption-aware lock variants, not even as no-ops kept for later;
spin locks hold no section at all.

## Consequences

- Priority inheritance and adaptive spinning stay: they decide which
  runnable thread runs next and whether an owner is on a CPU, not whether
  kernel code can be preempted.
- Making the kernel preemptible later means revisiting this crate: spin
  locks would need a section that holds off preemption, and a mutex that
  defers its holder's preemption, like Zircon's `CriticalMutex`, would
  come back into question.
  The crate is its own module so that change stays in one place.
```

Relative link from `crates/lock/docs/adr/` to root `docs/adr/` is
`../../../docs/adr/…`. Title can stay *Preemption is a non-goal* —
same decision, crate-local application.
