# Portable subsystems are modularized behind a `Platform` trait

Standing design principle. A portable subsystem lives in its own
workspace crate (`crates/lock`, `crates/clock`, `crates/collections`)
with zero arch imports. Every machine- or kernel-specific service
arrives through a small `Platform` trait — a zero-sized type parameter
(lock: `Mutex<T, P: Platform>`) or a stored value over composed traits
(clock: `TimeCounter + Calendar + TimePage`). The crate
holds no arch code and no kernel imports: the invariant is that
everything hardware- or kernel-specific arrives through the trait.

Flavours are generated by macros over one backend. Debug-only checks
and host fakes are gated with `cfg` (`debug_assertions`, `test`,
`loom`), not with Cargo features; a backend is selected by *who
implements* `Platform`, not by a feature flag.

The established pattern is `crates/lock` and `crates/clock`; their
decisions sit with every other ADR in `docs/adr/` (ADR 0012). The
`wip-mach` crate applies it to the whole
machine-independent core (ADR 0014). New subsystems follow this
principle silently — only a *deviation* needs a new ADR.

## Considered Options

- **Feature-flag backends**: each implementation behind a Cargo
  feature. Rejected: features compose into an untestable matrix and
  cannot express "the kernel supplies these services" as clearly as
  a trait impl.
- **Arch modules inside each crate**: `#[cfg(target_arch)]` branches
  in the subsystem. Rejected: it drags the machine into a portable
  crate and blurs the seam this principle exists to keep.

## Consequences

- A portable crate is host-testable and loom-testable on its own; the
  kernel is only one of its implementors.
- Adding a service to `Platform` is a deliberate interface change
  against every implementor, not a free helper call.
